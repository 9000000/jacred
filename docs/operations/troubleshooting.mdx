Начните с проверки процесса, health endpoint и логов:

```bash
systemctl status jacred
curl -f http://127.0.0.1:9117/health
journalctl -u jacred -n 100 --no-pager
```

<AccordionGroup>
  <Accordion title="Приложение не запускается">
    1. Проверьте, что рядом с бинарником существует читаемый `init.yaml` или `init.conf`.
    2. Проверьте, свободен ли порт:

    ```bash
    ss -ltnp | grep ':9117'
    ```

    3. Если .NET сообщает об отсутствующем ICU, установите пакет для вашей системы:

    ```bash
    sudo apt update
    sudo apt install libicu-dev
    ```

    Для Docker посмотрите вывод `docker logs jacred`.
  </Accordion>

  <Accordion title="FileDB не обновляется">
    Проверьте задания и активные фоновые операции:

    ```bash
    crontab -l
    curl http://127.0.0.1:9117/health/background-jobs
    tail -f /opt/jacred/Data/log/rutor.log
    ```

    Docker-образ не запускает cron внутри контейнера: `/cron/*` парсеры нужно вызывать с хоста или отдельного планировщика. Индекс `masterDb` процесс сам пишет в `Data/masterDb.bz` примерно каждые 10 минут, если он менялся. `GET /jsondb/save` оставьте в crontab для немедленного сброса перед остановкой или обновлением. После рестарта с пустым поиском проверьте mtime `Data/masterDb.bz` и лог FDB на `masterDb persist error`. Если вы меняете конфигурацию вручную, редактируйте рабочий файл рядом с бинарником, а не только копию под `Data/`.
  </Accordion>

  <Accordion title="ParseAll остановился после рестарта">
    Цикл лежит в `Data/temp/{slug}_parseAllCycle.json` и `{slug}_taskParse.json`. Через ~45 с после старта `ParseAllResumeWorker` вызывает `ResumeParseAll`; cron `*/15` — запасной путь.

    ```bash
    curl http://127.0.0.1:9117/cron/maintenance/ParseAllStatus
    curl http://127.0.0.1:9117/cron/maintenance/ResumeParseAll
    curl http://127.0.0.1:9117/health/background-jobs
    ```

    `idle` при pending = 0 — цикл закончен; новый круг даёт cron `ParseAllTask`, не Resume. `work` — задача уже идёт.
  </Accordion>

  <Accordion title="ParseAll ходит на пустые страницы за хвостом листинга">
    Карта в `Data/temp/{slug}_taskParse.json` выросла дальше живого пейджера. `UpdateTasksParse` читает пейджер раздела и удаляет слоты за последней страницей. Пустой HTML при этом **не** обнуляет карту.

    ```bash
    curl http://127.0.0.1:9117/cron/{slug}/UpdateTasksParse
    grep pruned /opt/jacred/Data/log/{slug}.log
    ```

    Активный обход смотрите на `/jobs` или в `GET /health/background-jobs`. Подробнее: [обзор трекеров](/trackers/overview).
  </Accordion>

  <Accordion title="ParseAll крутит одни и те же страницы (pending не падает)">
    Цикл не ротируется, пока pending > 0. Три подряд **сбоя** fetch/parse снимают слот (`ParseAll skip slot page=… after 3 failures`) — цикл сам уходит с дырки. Если `parsePage` не помечает пустой, но **валидный** листинг как done (это не сбой), обход вечно ретраит дырки (Rutor: `pending=4/3958`). Скрипт ниже — для таких дырок и для циклов, которые зависли до fail budget.

    Сначала убедитесь, что ParseAll этого слага не идёт (`/health/background-jobs`), затем:

    ```bash
    python3 scripts/parseall_cycle.py --dir /opt/jacred/Data/temp status
    python3 scripts/parseall_cycle.py --dir /opt/jacred/Data/temp recrawl --skip-pending
    python3 scripts/parseall_cycle.py --dir /opt/jacred/Data/temp recrawl --skip-pending --apply
    ```

    Без слага скрипт трогает все trio ParseAll (`anibelka`, `kinozal`, `korsars`, `megapeer`, `nnmclub`, `rutor`, `rutracker`, `toloka`, `torrentby`, `ultradox`) у которых `0 < pending ≤ --max-pending` (дырки, не живой обход). Потом `curl /cron/{slug}/ParseAllTask` на те слаги, что изменились. `skip-pending` только снимает текущие дырки (следующий ParseAll начнёт полный круг и снова встанет). `recrawl --skip-pending` — новый цикл без этих слотов.
  </Accordion>

  <Accordion title="parse отвечает work, lock held for Ns">
    Повторный `GET /cron/{slug}/parse` (и Bitru `/backfill`) пропускается, пока жив parse-lock. В теле: `work, lock held for Ns`. Секунды — сколько уже держится замок, не ошибка. Часы без прогресса в логе трекера — зависший lock: перезапустите процесс. Bitru `backfill` делит замок с `:50` `parse`: не поднимайте `pages` в crontab.
  </Accordion>

  <Accordion title="API возвращает 401 или 403">
    `401` обычно означает, что обязательный ключ не передан. `403` означает неверный ключ или запрещённый сетевой контекст.

    ```bash
    curl -H "X-Dev-Key: YOUR_DEV_KEY" \
      http://127.0.0.1:9117/cron/maintenance/Status
    ```

    Для `/api/v1.0/config*`, `/cron/*`, `/dev/*` и `/jsondb*` через reverse proxy нужен `devkey`. Проверьте [матрицу доступа](/operations/access-matrix).
  </Accordion>

  <Accordion title="Rutracker возвращает 403">
    Убедитесь, что FlareSolverr доступен и включён:

    ```bash
    curl http://127.0.0.1:8191/
    curl http://127.0.0.1:9117/cron/cloudflare/Warmup
    ```

    Первый warmup может выполняться несколько минут. На VPS с датацентровым IP challenge может потребовать residential/ISP-прокси для FlareSolverr. См. [настройку Rutracker](/trackers/rutracker).
  </Accordion>

  <Accordion title="403 или 503 без признаков Cloudflare">
    В логе Host один раз на хост:

    ```text
    {host}: 403 без признаков Cloudflare — браузерный fallback не сработает; проверьте Referer/зеркало/лимит
    ```

    FlareSolverr и cffetch этот ответ не исправят: это не CF-challenge. Проверьте Referer (Ultradox), зеркало, лимит запросов. Тот же статус с `cf-mitigated` / «Just a moment…» по-прежнему идёт через Warmup, FlareSolverr и cffetch.
  </Accordion>

  <Accordion title="Kinozal парсится, но новых раздач нет">
    `kinozal.guru` за Cloudflare. Списки и info-hash идут через FlareSolverr GET. Проверьте:

    ```bash
    python3 scripts/flaresolverr_kinozal_cf_check.py
    ```

    Прямой curl получит `403` / «Just a moment». В FlareSolverr нужны listing rows и `Инфо хеш` на шаге GET. Страницы года с «Нет активных раздач» (~15 KB) — пустая выдача, не stale-вкладка; см. `scripts/kinozal_empty_tail_check.py`. См. [Kinozal](/trackers/kinozal).
  </Accordion>

  <Accordion title="Прокси или Tor не работает">
    Проверьте порт Tor, URI прокси и регулярное выражение `globalproxy.pattern`:

    ```bash
    ss -ltnp | grep ':9050'
    ```

    Для Tor и любого SOCKS5 используйте URI со схемой, например `socks5://127.0.0.1:9050`. Запись `host:port` без схемы идёт как HTTP-прокси и на SOCKS5-сервере не работает. Если для HTTP-прокси включён `useAuth`, а SOCKS5 авторизацию не принимает, поставьте `useAuth: false`. Подробнее читайте в разделе [Прокси](/configuration/proxy).
  </Accordion>

  <Accordion title="JacRed потребляет много памяти">
    Уменьшите `maxreadfile`, настройте ротацию логов и проверьте число внешних Chromium-сессий. Одна сессия FlareSolverr может занимать сотни мегабайт.

    Включайте `evercache` только после оценки доступной памяти и нагрузки. Для контейнера задайте подходящий лимит памяти.
  </Accordion>
</AccordionGroup>

Если FileDB показывает несогласованные записи, сначала выполните read-only проверку из раздела [Обслуживание FileDB](/operations/maintenance).
